# Permanent per-skill downloads

Each skill has one stable address:

```text
https://github.com/maxpkg-dev/max-ultra-mcp-community-skills/releases/download/<id>-latest/<id>-latest-max-ultra-mcp.zip
```

The numbered `<id>-vX.Y.Z` releases remain immutable by project policy. Only the separate,
explicitly marked `<id>-latest` release can be refreshed. Its tag stays anchored at creation;
its current ZIP source is identified in the rolling release notes and the numbered history.
Do not use repository-global `/releases/latest`: this catalog has independent skills.

## Automatic paths

- A manually published stable numbered release triggers `.github/workflows/download.yml`.
  It checks out the trusted default branch, reads event data as data, and handles only the
  exact currently accepted skill/version. It never executes a submitted package.
- `tools/release.py` invokes the same updater after publishing/verifying numbered assets.
  This is necessary because events generated by GITHUB_TOKEN do not start another workflow.
- Both paths validate the source package, match its public numbered ZIP and checksum, select
  the greatest stable X.Y.Z release for that skill, and reject stale/unknown source. Other
  skills, drafts, prereleases, and rolling tags cannot win the version selection.
- Both confirm the external stable URL and update catalog metadata/generated pages using a
  normal catalog-only commit/push. No manual link maintenance or extra commit is normally needed.
  A rejected protected-branch push is reported, never bypassed. New entries become downloadable
  after this confirmation; existing stable URLs continue to work independently of metadata text.

The automatic numbered-release gate remains unchanged. Manual GitHub publication still
refreshes aliases when ENABLE_SKILL_RELEASES is off. Unknown release tags do not publish
anything. Alias publication is excluded by the workflow guard, avoiding recursion. Both
workflows share `accepted-skill-releases` concurrency; do not run a local updater concurrently.
Release-event workflow files must exist at the accepted release commit; initial/older releases
can be seeded with the explicit recovery workflow instead.

## Integrity, retries, and limitations

1. Validate current default-branch metadata and rebuild deterministically. Verify both
   numbered assets byte-for-byte before any alias mutation.
2. Find/create the marked rolling release. Reject an unmanaged or immutable alias. Never
   change global immutability settings or retarget an existing tag.
3. Upload a content-addressed candidate and download it back for verification. An incomplete,
   corrupt, missing, or unverified candidate cannot displace the old live ZIP.
4. Recheck latest-version selection and the current asset ID. Rename the old asset to a
   retained backup, then rename the verified candidate to the fixed download filename.
5. On a recoverable error, inspect the remote result before restoring the old name. A timeout
   after a successful rename must not roll back the new file. On interruption, rerunning from
   current accepted source can promote the already-verified candidate. No old bytes are deleted.
6. Recheck API and public HTTP bytes, then update release notes/catalog evidence. Numbered
   release assets/tags are never mutated by the alias updater.

GitHub has no atomic release-asset replacement API. There is a brief interval between the two
renames when the fixed URL may return 404. A hard process kill or API outage in that interval
may require a retry; backup and candidate bytes remain present. The implementation cannot
promise zero downtime or automatic rollback during a network outage. Download redirects/CDN
or browser caches may briefly retain old content. Use the immutable numbered URL and checksum
for reproducible version pinning. The stable endpoint is designed for convenience, not a
transactional package registry. Concurrent out-of-band asset editing is unsupported.

GitHub immutable releases cannot be refreshed after publication. The updater checks the
alias's immutable flag before writes and after first publication; if GitHub locks a new alias,
it stops and reports the need for a different endpoint. It never disables protection. Reading
global immutability settings requires admin permission, so Actions uses per-release evidence.
This repository's setting was inspected as disabled during initial implementation.

Do not manually replace failed-upload candidates or delete retained backups casually. If a
candidate upload is corrupt/incomplete, that run stops with the last good download retained.
A retry uploads a fresh candidate under a unique name; it never promotes the failed upload. Numbered versions are never a repair
target. A newly published but unaccepted higher version blocks promotion rather than guessing.

## Recovery only

Use **Actions > Refresh published skill download > Run workflow**, select the default branch,
and supply the exact skill ID. This shares the publisher's concurrency and updates metadata
in the same run. It does not create a numbered release or enable version publishing.

Alternatively, with authenticated GitHub CLI or GH_TOKEN, from the current accepted checkout:

```sh
python tools/rolling.py --skill archviz-master-yuriy-bobak
```

This local command verifies the public numbered release, initializes/repairs only its managed
alias, and confirms local metadata/pages. Review and commit local metadata changes if present.
The normal release-event and integrated-publisher paths perform the catalog commit automatically.
Do not run local recovery simultaneously with a workflow; inspect Actions first.

## Official GitHub behavior

- [Release links](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases): repository latest is not a per-skill selector.
- [Release asset API](https://docs.github.com/en/rest/releases/assets): duplicate names conflict; asset names can be updated.
- [Release management and immutability](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).
- [Triggering workflows](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow): GITHUB_TOKEN recursion restrictions.
